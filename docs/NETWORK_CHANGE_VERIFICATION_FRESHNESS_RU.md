# Актуальность проверки сетевых изменений

## Назначение

Контракт актуальности проверки дополняет безопасную поэтапную модель сетевых изменений Control Center. Он позволяет перед применением изменения однозначно проверить, что результаты обязательных проверок относятся к тому же плану и той же ревизии, не устарели и не были заменены неполными либо повреждёнными данными.

Контракт является только источником доказательств готовности. Он не выдаёт разрешение на изменение сети, не выполняет команды и не содержит учётные данные, адреса управляющих систем или произвольные исполняемые данные.

## Привязка доказательств

Доказательство содержит:

- версию схемы `network.change.verification-freshness/v1`;
- `plan_id` в форме `sha256:<digest>` точного канонического плана;
- `revision_id` точной ревизии;
- время формирования итоговой проверки;
- набор именованных проверок со статусом `PASS` или `FAIL`;
- SHA-256 digest доказательства каждой проверки;
- время наблюдения каждой проверки.

Проверка считается пригодной только для указанной пары `plan_id` + `revision_id`. Несовпадение любого из идентификаторов отклоняется fail-closed.

Для оценки, привязанной непосредственно к `ChangePlan`, обязательный набор проверок выводится из полного списка `ConnectivityProbe.ID` этого канонического плана. Вызывающая сторона не может сократить этот список своей политикой: каждый probe точного плана должен иметь собственное свежее доказательство. Набор evidence также не может быть расширен проверками от другого плана: любой check, которого нет среди `ConnectivityProbe.ID` текущего плана, отклоняется как смешанное доказательство вместо молчаливого игнорирования.

Перед оценкой целостность самого плана проверяется в два этапа: сначала `plan_id` пересчитывается по всему фактически переданному envelope, затем план повторно строится из разрешённых входных контрактов и сравнивается с тем же идентификатором. Поэтому изменение со старым `plan_id` не только интерфейсов, forwarding, probes или таймаутов, но также версии схемы, default-deny признака, staged steps либо иных полей канонического плана отклоняется fail-closed.

Максимальное число verification evidence согласовано с максимальным числом probes сетевого плана — 128. Поэтому любой план, допустимый по контракту `network.change.plan/v1`, может быть полностью представлен verification evidence без искусственного усечения списка проверок.

Сериализованное verification evidence имеет отдельную строгую границу потребления: неизвестные поля, trailing JSON, дубли check-имён и неканонические идентификаторы отклоняются до оценки freshness. Эта проверка формы не подменяет временную проверку — доверенное текущее время и freshness policy применяются отдельно.

## Политика актуальности

Политика задаёт максимальный возраст доказательства и допустимое отклонение часов в будущее. Для низкоуровневой проверки может передаваться закрытый список обязательных проверок; для проверки конкретного `ChangePlan` этот список всегда формируется из самого плана.

Интервал актуальности имеет строгую правую границу: момент `observed_at + max_age` уже считается истёкшим. То же правило применяется к итоговому `verified_at` и к `expires_at` preflight admission. Это исключает неоднозначность на точной границе срока и не позволяет использовать доказательство ещё один переход state machine в момент его истечения.

Результат `ready=true` возможен только одновременно при всех условиях:

1. итоговое доказательство не старше допустимого возраста;
2. каждая обязательная проверка присутствует ровно один раз;
3. каждая обязательная проверка имеет статус `PASS`;
4. время каждой обязательной проверки находится в допустимом окне актуальности;
5. время проверки не выходит за границы итогового verification envelope;
6. все SHA-256 digest имеют корректный формат;
7. список обязательных проверок не содержит дубликатов;
8. при plan-bound оценке присутствует свежее доказательство для каждого `ConnectivityProbe.ID` точного канонического плана;
9. при plan-bound оценке отсутствуют checks, не объявленные текущим планом.

Отсутствующая, устаревшая или завершившаяся `FAIL` проверка даёт `ready=false`. Повреждённые, неоднозначные или противоречивые входные данные отклоняются как ошибка контракта.

## Preflight admission

После оценки актуальности формируется отдельное детерминированное доказательство `network.change.verification-preflight-admission/v1`. Оно связывает результат с точными `plan_id`, `revision_id`, digest исходного verification evidence и версией state machine в состоянии preflight.

Admission содержит время оценки и, для положительного результата, срок действия. `admission_id` является SHA-256 identity канонического содержимого admission. Любая подмена плана, ревизии, evidence, версии машины, результата или срока действия нарушает identity и отклоняется fail-closed.

Положительный admission может породить только типизированное событие `preflight_passed` и только если одновременно выполняются условия:

- state machine всё ещё относится к тому же `plan_id`;
- машина всё ещё находится в состоянии preflight;
- `machine_version` не изменился;
- событие не создаётся раньше времени оценки;
- событие создаётся строго раньше `expires_at`.

Даже при `ready=true` поля `execution_authorized` и `production_mutation_allowed` всегда равны `false`. Admission не является разрешением на изменение сети, не открывает временное apply-окно и не выполняет adapter action. Фактическое применение остаётся отдельным последующим этапом state machine с собственной авторизацией и проверками.

## Безопасность

Контракт сохраняет следующие инварианты:

- решение детерминировано для одинаковых входных данных и времени оценки;
- неизвестные статусы не трактуются как успех;
- дубликаты доказательств не используются для подмены результата;
- данные из будущего за пределами допустимого clock skew отклоняются;
- истёкшее доказательство нельзя переиспользовать для нового сетевого изменения;
- точный момент истечения уже считается невалидным, без дополнительного граничного окна;
- изменение состава probes, параметров плана или `revision_id` требует нового evidence для нового `plan_id`;
- весь фактически переданный `ChangePlan` должен соответствовать своему `plan_id`; старый идентификатор нельзя переиспользовать после изменения envelope-полей;
- evidence от другого плана нельзя примешать к текущему набору обязательных проверок;
- вызывающая сторона plan-bound оценки не может ослабить проверку сокращением required-check list;
- preflight admission связан с точной версией state machine и не может быть переиспользован после изменения её состояния;
- положительный результат не заменяет отдельные этапы авторизации, staged apply, connectivity probes и автоматического rollback;
- контракт не предоставляет production-mutation authority.

## Использование

Контракт предназначен для связывания preflight/verification evidence с точным сетевым change plan непосредственно перед переходом к разрешённому этапу применения. После изменения плана, ревизии, verification evidence или версии state machine прежнее доказательство должно считаться неприменимым и формироваться заново.
