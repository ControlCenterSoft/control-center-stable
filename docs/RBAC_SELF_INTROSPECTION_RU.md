# Control Center — просмотр собственных прав доступа

## Назначение

Control Center предоставляет аутентифицированному пользователю read-only представление его собственных назначений RBAC. Это позволяет интерфейсу и пользователю понять, какие роли, области действия и разрешения применены к текущей учётной записи, не предоставляя возможности просматривать права других пользователей.

API: `GET /api/v1/identity/self/access`.

## Граница доступа

Идентификатор пользователя берётся только из текущей проверенной сессии. Запрос не принимает целевой `user_id` и не предоставляет административный поиск по субъектам. Дополнительные параметры запроса не меняют субъект: результат всегда относится к текущей identity.

До завершения обязательной смены первоначального пароля `admin` этот API недоступен, как и остальные обычные функции Control Center.

## Формат результата

Ответ содержит:

- `subject_id` — идентификатор текущей identity;
- `grants` — список назначений, каждое из которых содержит имя роли, scope и разрешения этой роли.

Scope может быть `global`, `tenant`, `site` или `resource`. Для `global` идентификатор scope отсутствует; для остальных типов он обязателен.

Разрешения внутри назначения выдаются в стабильном порядке. Явный wildcard `*` означает, что соответствующая роль предоставляет все разрешения в пределах данного scope. API не преобразует wildcard в заранее зафиксированный список разрешений, поэтому появление новых разрешений не делает старое представление ошибочно неполным.

Пользователь без RBAC bindings получает собственный `subject_id` и пустой список `grants`. Пустой список не превращается в разрешение: основной authorizer по-прежнему работает deny-by-default.

## Безопасность и аудит

Операция является только чтением и не создаёт, не изменяет и не удаляет роли или bindings.

Перед возвратом данных Control Center обязан успешно сохранить Audit event `authorization.self_access_read` с текущим пользователем как `actor_id` и `subject_id`. Если обязательное Audit-хранилище недоступно, список прав не возвращается и запрос завершается ошибкой доступности. Это сохраняет fail-closed границу для security-sensitive introspection.

Ответы не должны кэшироваться (`Cache-Control: no-store`). Значения паролей, session tokens, cookie, token digests и другие credentials в ответ и Audit evidence не включаются.

## Не является административным API

Этот endpoint не заменяет управление пользователями и RBAC. Для чтения или изменения ролей и bindings других пользователей должны использоваться отдельные административные API с явными permissions, scope checks и Audit.

## Проверка

Корректная реализация должна подтверждать как минимум:

- результат относится только к identity текущей сессии;
- пользователь не может подменить субъект параметром запроса;
- unbound identity получает пустой список без неявных прав;
- first-login password-change boundary не обходится;
- отказ Audit блокирует выдачу security-sensitive результата;
- PostgreSQL и in-memory authorizer возвращают согласованную модель role/scope/permissions;
- порядок grants и permissions детерминирован.
