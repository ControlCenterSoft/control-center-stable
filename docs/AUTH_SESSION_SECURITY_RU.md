# Control Center — безопасность пользовательских сессий

## Назначение

Control Center предоставляет локальной аутентифицированной учётной записи собственный контур управления активными сессиями. Пользователь может увидеть только свои действующие сессии, завершить одну выбранную сессию или немедленно завершить все свои активные сессии.

Контур предназначен для случаев потери устройства, подозрения на компрометацию браузерной сессии, проверки неизвестного входа или необходимости принудительно повторить аутентификацию на одном либо всех клиентах.

## Срок жизни и тайм-аут бездействия

Каждая сессия имеет две независимые временные границы:

- абсолютный `expires_at`, который никогда не продлевается пользовательской активностью;
- тайм-аут бездействия, рассчитанный от `last_activity_at`.

По умолчанию абсолютный срок жизни сессии составляет 8 часов, а допустимое непрерывное бездействие — 2 часа. Политика задаётся для экземпляра Control Center параметрами `CC_AUTH_SESSION_TTL` и `CC_AUTH_SESSION_IDLE_TIMEOUT`. Значения разбираются как длительности Go, например `8h`, `90m` или `24h`.

Абсолютный TTL должен находиться в диапазоне от 1 минуты до 7 суток. Idle timeout также не может быть меньше 1 минуты и не может превышать абсолютный TTL. Некорректная комбинация отклоняется при загрузке конфигурации: Control Center не стартует с невалидной session policy и не заменяет ошибочное значение молча более слабым значением.

`last_activity_at` обновляется только после успешной аутентификации уже действующей сессии. Запрос с отозванной, абсолютной истёкшей или idle-expired сессией не обновляет активность и получает обычный отказ аутентификации. Активность никогда не переносит `expires_at` дальше первоначально выданной абсолютной границы.

Данные активности сохраняются в durable session storage, поэтому рестарт Control Center не обнуляет idle timeout и не делает неактивную сессию снова действующей.

## API

### Просмотр эффективной политики сессий

`GET /api/v1/auth/session-policy`

Операция возвращает фактически применяемую текущим экземпляром политику:

- `absolute_ttl_seconds` — абсолютный срок новой сессии;
- `idle_timeout_seconds` — допустимый интервал бездействия;
- `activity_refreshes_idle_deadline=true` — успешная активность переносит только idle deadline;
- `activity_extends_absolute_expiry=false` — абсолютный срок никогда не продлевается активностью.

Endpoint требует действующую аутентифицированную сессию и не обходится до завершения обязательной смены первоначального пароля. Чтение политики фиксируется в Audit как `auth.session_policy_read` с actor/subject текущей identity и эффективными временными значениями. Если обязательный Audit недоступен, политика не возвращается и запрос завершается fail-closed.

### Просмотр собственных активных сессий

`GET /api/v1/auth/sessions`

Операция:

- требует действующую аутентифицированную сессию;
- недоступна до завершения обязательной смены первоначального пароля после чистой установки;
- возвращает только активные сессии текущей identity;
- исключает сессии, уже превысившие тайм-аут бездействия;
- помечает сессию, из которой выполнен запрос, полем `current=true`;
- показывает `last_activity_at` и эффективный `idle_expires_at`, ограниченный абсолютным `expires_at`;
- может показывать время создания/истечения, source IP и ограниченный User-Agent для распознавания собственного устройства;
- никогда не возвращает session token, token digest, password hash или иной credential;
- не принимает идентификатор другого пользователя.

Список учитывает абсолютный срок действия сессии, idle timeout, признак отзыва и текущую credential version. Сессия со старой credential version не считается действующей даже при наличии записи в storage.

### Завершение одной собственной сессии

`DELETE /api/v1/auth/sessions/{sessionID}`

Операция завершает только выбранную активную сессию, если она принадлежит текущей identity. Неизвестный, malformed, абсолютный истёкший, idle-expired, уже отозванный или принадлежащий другому пользователю идентификатор возвращается единообразно как `404`, чтобы session-control API не превращался в механизм перечисления чужих сессий.

Если пользователь завершает текущую браузерную сессию, cookie удаляется и следующий защищённый запрос требует нового входа. Завершение другой собственной сессии не должно отзывать текущую.

### Завершение всех собственных сессий

`POST /api/v1/auth/sessions/revoke-all`

Операция:

- отзывает все активные сессии текущей учётной записи, включая сессию, из которой выполнен запрос;
- после успешного выполнения требует нового входа;
- не принимает идентификатор другого пользователя и поэтому не является административным API управления чужими сессиями;
- не возвращает и не записывает в Audit значения session token, cookie или пароля.

При cookie-аутентификации ответ также удаляет cookie текущей сессии. Успешный ответ имеет статус `204 No Content`.

## Audit и fail-closed граница

Просмотр эффективной session policy фиксируется событием `auth.session_policy_read`. В Audit сохраняются только безопасные эффективные значения TTL/idle timeout и идентичность запроса, без session token или cookie. Невозможность записать обязательное событие блокирует выдачу policy.

Просмотр собственных сессий фиксируется событием `auth.sessions_list` без credential material.

Перед отзывом одной сессии Control Center обязан успешно записать `auth.session_revoke` со статусом `requested`, actor/subject текущей identity и идентификатором собственной целевой сессии. Если обязательный Audit недоступен, mutation не начинается. После изменения записывается `success`; конкурентно исчезнувшая/уже изменённая цель фиксируется как `failed` без раскрытия токенов.

Перед отзывом всех сессий Control Center обязан успешно записать `auth.sessions_revoke_all` со статусом `requested`. Если обязательный Audit недоступен, отзыв сессий не начинается. После выполнения сохраняется `success` и количество отозванных сессий; при ошибке session store фиксируется `failed` без записи чувствительных значений.

Idle-timeout проверяется внутри основной границы `Authenticate`: неактивная сессия отклоняется до выдачи аутентифицированной identity. Само чтение/обновление `last_activity_at` не создаёт отдельное audit-событие на каждый запрос, чтобы security audit не превращался в журнал HTTP-трафика. Значимые login/logout/revoke операции продолжают иметь отдельные события Audit.

Эти операции не изменяют пароль, RBAC-привязки, Desired State или инфраструктурные ресурсы.

## Проверяемые инварианты

- конфигурация не принимает absolute TTL меньше 1 минуты или больше 7 суток;
- idle timeout не может быть меньше 1 минуты или превышать absolute TTL;
- эффективная политика доступна после аутентификации и обязательной first-login смены пароля;
- policy read не возвращается без обязательного audit evidence;
- список не содержит чужих, абсолютных истёкших, idle-expired, отозванных или credential-stale сессий;
- успешное использование действующей сессии обновляет `last_activity_at`;
- неуспешная попытка использования idle-expired сессии не продлевает её жизнь;
- `idle_expires_at` никогда не находится позже абсолютного `expires_at`;
- текущая сессия в списке определяется явно;
- завершение выбранной другой собственной сессии не влияет на текущую;
- завершение текущей сессии делает её немедленно недействительной и удаляет cookie;
- malformed и foreign session ID не позволяют определить существование чужой сессии;
- две и более активные сессии одного пользователя становятся недействительными после одного успешного `revoke-all`;
- повторное использование отозванного token приводит к отказу аутентификации;
- невозможность записать обязательное pre-mutation audit evidence блокирует mutation до изменения состояния;
- обязательный first-login password-change boundary остаётся приоритетным и не обходится через session-control API.

Формальный HTTP-контракт находится в `api/openapi-auth-session-controls.yaml`.
