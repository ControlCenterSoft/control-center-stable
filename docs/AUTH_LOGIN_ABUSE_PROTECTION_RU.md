# Защита входа от перебора и credential spraying

Статус: development contract, не отдельный релиз.

## Назначение

Контур входа Control Center ограничивает повторяющиеся неуспешные попытки аутентификации до дорогостоящего создания сессии. Защита не изменяет внешний контракт ошибки: неверный пароль, неизвестное имя пользователя и временная блокировка отвечают одинаковой ошибкой `invalid_credentials`.

## Базовая политика

По умолчанию используются две независимые границы:

- по нормализованному имени пользователя: 8 неуспешных попыток за 10 минут;
- по адресу источника: 30 неуспешных попыток за 10 минут;
- после достижения любой границы новые попытки по соответствующему ключу блокируются на 15 минут;
- одновременно хранится не более 10 000 ключей защиты; при достижении границы вытесняется самый давно использованный ключ.

Ключи в памяти представлены SHA-256 digest, а не исходным именем пользователя или IP-адресом. Значения паролей, session token и token digest в состоянии защиты не сохраняются.

## Защита от enumeration

Контур не сообщает клиенту, существует ли пользователь. Для неизвестного пользователя до достижения ограничения выполняется тот же password-hash verification с timing equalizer, который используется существующей моделью аутентификации. После активации ограничения запрос отклоняется до password verification как `invalid_credentials` и для существующих, и для несуществующих имён.

Событие `auth.login` продолжает записываться в Audit. При срабатывании ограничения внутренний audit detail содержит `login_protection=blocked`, но этот признак не возвращается клиенту и не меняет HTTP-код/тело ответа.

## Семантика успешного входа

Успешная аутентификация очищает накопленные account-scoped failures для конкретного пользователя. Source-scoped history не очищается успешным входом, чтобы один известный корректный credential не мог сбросить защиту источника при username spraying.

## Граница реализации

Текущая реализация является bounded process-local защитой для локального auth service и не требует новой схемы БД. Она не должна описываться как cluster-wide rate limit. Для будущей многопроцессной/распределённой эксплуатации потребуется совместимый shared/durable backend с той же fail-closed и anti-enumeration семантикой.

## Критерии qualification

Перед продвижением пакет должен подтвердить:

- блокировку account-scoped перебора независимо от IP-адреса источника;
- блокировку username spraying по одному источнику;
- одинаковый внешний `invalid_credentials` для wrong/missing/blocked случаев;
- автоматическое снятие временной блокировки после истечения окна;
- bounded memory behavior;
- отсутствие паролей, session token и token digest в limiter state/Audit;
- отсутствие регрессии first-login password-change и обычного session lifecycle.
