# Безопасное изменение сети — контракт 0.6

Контракт `network.change.plan/v1` задаёт типизированную, независимую от ОС последовательность безопасного изменения сети. Он не применяет конфигурацию, не вызывает сетевые backend-адаптеры и не содержит произвольных команд, адресов управляющих узлов или учётных данных.

## Последовательность

1. Создать Recovery Snapshot и сохранить его идентификатор.
2. Выполнить preflight текущего сетевого контракта, управляющего пути и forwarding policy.
3. Открыть ограниченное по времени окно временного применения.
4. Выполнить обязательные connectivity probes для всех изменяемых интерфейсов и отдельную проверку Control Plane через `MANAGEMENT` или `LAN`.
5. Зафиксировать изменение только после успешного завершения всех probes. Любая ошибка или timeout после временного применения переводит изменение в `rollback_pending`.

Если snapshot или preflight не подтверждены, изменение завершается в `failed_closed` до временного применения. Если rollback не подтверждён в отведённый срок, состояние также становится `failed_closed`; успешный результат в этом случае не заявляется.

## Multi-NIC и сетевые зоны

- План содержит явный список интерфейсов, их зоны и признак изменения.
- Каждый изменяемый интерфейс обязан иметь типизированную проверку связности.
- Probe обязан ссылаться на интерфейс и совпадающую с ним зону.
- Межзонная маршрутизация по умолчанию запрещена.
- Для WAN forwarding обязательны одновременно явное разрешение и назначенная роль Edge Gateway.
- Наличие интерфейсов WAN и LAN само по себе не создаёт routing, NAT или port forwarding.

## Детерминизм и повторная доставка

Интерфейсы, forwarding intents и probes приводятся к каноническому порядку. `plan_id` вычисляется как SHA-256 канонического плана. State machine использует optimistic version и идентификатор события:

- повтор того же события не изменяет состояние и версию;
- повтор идентификатора с другим содержимым отклоняется;
- устаревшая версия и неизвестный переход отклоняются;
- результат `committed` возможен только после всех объявленных probes.

Все фазовые timeout обязательны, положительны и ограничены 15 минутами. Probe timeout не может превышать временное apply-окно.
